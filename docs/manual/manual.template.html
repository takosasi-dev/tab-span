この説明書は、測定用ツール(Phase 0 の Probe)の物です。
{{ app.name }} は、Android の端末を Windows PC の拡張モニターにするソフトとして開発中です。いま配っているのは、設計を決めるための測定用ツールだけで、まだ PC の画面を端末に映すことはできません。アプリ本体は、これから作ります。

この説明書の出力の例のうち、PC のモニター名・アダプター名・デバイス ID・証明書の指紋は、すべて架空の値です。端末の型番(dtab d-01J)とデコーダーの名前は実物です。

1. はじめに(このツールでできること・できないこと)

{{ app.name }} は、机の上の Android の端末を、Windows PC の 2 枚目の画面として使うためのソフトです。完成すると、PC が画面を取り込んで H.264 に圧縮し、USB か LAN の TLS で端末へ送り、端末が復号して全画面で映し、触った位置を PC に返す形になります。

いまは、その設計を決める前に「この PC とこの端末で、何がどれくらいの速さでできるか」を測る段階(Phase 0)です。この説明書は、そのための測定用ツール 2 つの使い方を書いた物です。

測定用ツールは 2 つ

名前動く場所やること
PC の Probe
TabSpan.Probe.exe		Windows PC(コンソール)モニターの一覧、画面の取り込み、H.264 の圧縮、adb の確認、TLS の待ち受け、モニターの取り外し、タッチの注入、時計の表示
Android の probe
(アプリ名「TabSpan Probe」)		Android の端末端末とデコーダーの調べ物、PC への TLS の接続テスト、置いた映像の復号のテスト

できること

  • PC のモニターの一覧を見る。モニターを 5 秒取り込んで、フレームが届くかを見る。
  • PC の H.264 のエンコーダーの一覧を見て、実際に 5 秒圧縮してみる。
  • 端末から PC へ、USB 経由で TLS 1.2 でつながるかを試す。
  • 端末のデコーダーが、どの大きさをどれくらいの速さで復号できるかを測る。

できないこと

  • PC の画面を端末に映すこと(アプリ本体がまだ無いため)。
  • 端末で触った位置を PC に返すこと。
  • LAN でつなぐこと(TLS のテストは USB の adb reverse 経由だけです)。
測定用ツールは、結果を画面に出すだけです。取り込んだ画面・圧縮した映像・結果をファイルに保存せず、127.0.0.1(自分自身)のほかへ通信しません。

端末で USB デバッグを有効にする

adb を使うには、端末の「USB デバッグ」を有効にします。メニューの名前と場所は機種で違います。よくある手順は次のとおりです。

  1. 端末の「設定」→「端末情報」(「タブレット情報」など)を開き、「ビルド番号」を 7 回続けて触ります。「開発者になりました」と出ます。
  2. 「設定」に増えた「開発者向けオプション」を開き、「USB デバッグ」を有効にします。
  3. 端末を USB で PC につなぎます。端末に「USB デバッグを許可しますか?」と出たら、PC の指紋を確かめて「許可」を押します。
  4. PC の PowerShell で adb devices を打ち、端末が device の状態で出れば準備できています。
USB デバッグを有効にすると、つないだ PC から端末を操作できるようになります。測定が終わったら、8 章の片付けで無効に戻すことを勧めます。

3. 入れ方

3.1 Android の probe を入れる

  1. ブラウザで {{ app.repo }}/releases/tag/v{{ app.version }} を開き、TabSpan-Probe-v{{ app.version }}-android.apk を PC に保存します。
  2. PowerShell で、保存したフォルダに移り、adb install TabSpan-Probe-v{{ app.version }}-android.apk を打ちます。Success と出れば入りました。
  3. 端末のアプリの一覧から「TabSpan Probe」を開きます。
仮の署名です。この APK は debug の鍵で署名した仮の物です。正式な鍵に変えた版は上書きで入らないので、いったん消してから入れ直します。

APK を端末で直接開いて入れることもできます。その場合は、提供元の不明なアプリを許す設定が要ります(場所は機種で違います)。

3.2 PC の Probe をビルドする

PC の Probe は、exe の隣に入る Windows SDK の DLL の再配布の条件をまだ確かめ終えていないため、ビルド済みの物を配っていません。ソースからビルドします。

  1. {{ app.repo }} から、ソースを取ります(「Code」→「Download ZIP」で取って展開するか、git clone)。
  2. PowerShell で、取ったフォルダ(README.md がある所)に移ります。
  3. dotnet build pc\TabSpan.sln -c Release を打ちます。最後に「ビルドに成功しました」(英語の環境では Build succeeded)と出れば終わりです。
  4. exe は次の場所にできます。
    pc\src\TabSpan.Probe\bin\Release\net10.0-windows10.0.22621.0\win-x64\TabSpan.Probe.exe

以下の例では、このフォルダに移ってから .\TabSpan.Probe.exe の形で動かします。管理者でない PowerShell から動かしてください。引数なしで動かすと、使い方の一覧が出ます。

3.3 adb の確認

端末をつないだ状態で .\TabSpan.Probe.exe adb を打つと、Probe が見つけた adb の場所と版、つながっている端末が出ます。端末のシリアルは先頭の 2 文字のほかを *** で伏せて出します。

出力の例(一部を略しています):

adb の場所: C:\Android\platform-tools\adb.exe (PATH)
(adb devices は、adb のサーバーが動いていなければ起こします。サーバーはこの Probe が終わっても残ります)

--- adb devices
List of devices attached
ab***	device

端末が unauthorized と出るときは、端末の画面の「USB デバッグを許可しますか?」に答えていません。

4. 使い方

4.1 Android の probe を開く

アプリを開くと、端末の情報・画面の大きさ・video/avc のデコーダーの一覧と、候補の大きさごとの申告と configure の試しが、自動で順に出ます。全部が終わると --- 終わり --- が出ます。

  • 出た行は、PC から adb logcat -s TabSpanProbe でも読めます。長い結果を写すときに便利です。
  • アプリを開いている間は、画面が消えないようにしています。

4.2 TLS のテスト(端末から PC へ TLS でつながるか)

PC の Probe が 127.0.0.1 で TLS の待ち受けを開き、端末のアプリが USB 経由でそこへつなぎます。つながったら、TLS の版・暗号スイート・証明書の指紋を両方に出します。

PC の待ち受けは 60 秒だけです。手順 3〜4 を 60 秒のうちに済ませます。間に合わなければ、手順 2 からやり直します。
アプリの仕事は 1 つずつ順に動きます。開いた直後の調べ物や復号のテストの途中で「TLS のテスト」を押すと順番待ちになり、60 秒が切れることがあります。手順 2 の前に、端末の画面に --- 終わり --- が出ていることを確かめます。
  1. 端末を USB で PC につなぎ、adb devices で device と出ることを確かめます。
  2. PowerShell で .\TabSpan.Probe.exe tls 47815 を打ちます。証明書の SHA-256 の指紋: の行が出て、60 秒の待ち受けが始まります。
  3. 別の PowerShell の窓で adb reverse tcp:47815 tcp:47815 を打ちます。端末の 127.0.0.1:47815 が、PC の 127.0.0.1:47815 につながります。
  4. 端末のアプリで、ポートの欄が 47815 になっていることを確かめて「TLS のテスト」を押します。
  5. 端末に TLS の結果: 成功 が出て、PC に 接続 1 (… 秒後): TLS の版 = … が出ます。
  6. PC の 証明書の SHA-256 の指紋 と、端末の 相手の証明書の SHA-256 の指紋 を見比べます。どちらも大文字の 16 進、区切りなしの 64 文字です。全部が同じなら、端末は確かに自分の PC につながっています。

端末側は adb から始めることもできます(手順 4 の代わり)。

adb shell am start -n io.github.takosasidev.tabspan.probe/.MainActivity --es action tls --ei port 47815

出力の例(指紋は架空の値):

PC   : 証明書の SHA-256 の指紋: 0A1B2C3D4E5F60718293A4B5C6D7E8F90A1B2C3D4E5F60718293A4B5C6D7E8F9
PC   : 接続 1 (12 秒後): TLS の版 = Tls12、暗号スイート = TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384
端末 : TLS の結果: 成功
端末 : protocol: TLSv1.2
端末 : 相手の証明書の SHA-256 の指紋: 0A1B2C3D4E5F60718293A4B5C6D7E8F90A1B2C3D4E5F60718293A4B5C6D7E8F9
証明書は検査していません。このテストは測定用なので、端末は相手の証明書を検査せずにつなぎます。相手を確かめる方法は、手順 6 の指紋の見比べだけです。

ポートを変えるときは、手順 2・3・4 の 47815 を全部同じ番号にします。

4.3 復号のテスト(端末のデコーダーの速さを測る)

PC で作った H.264 の映像を端末に置き、端末のデコーダーごとに、実際に復号して速さと遅れを測ります。

  1. 端末のアプリで、一度「復号のテスト」を押します。まだ映像が無いので ファイル 0 本 と出ますが、置き場: の行に、映像を置くフォルダが、次のような形で出ます。
    /storage/emulated/0/Android/data/io.github.takosasidev.tabspan.probe/files
    adb からは、次の場所が同じフォルダです。
    /sdcard/Android/data/io.github.takosasidev.tabspan.probe/files
  2. PC で試しの映像を作ります。ffmpeg で 1 本作る例(1280x800、30 fps、5 秒、8 Mbps)。紙面では折り返していますが、1 行で打ちます。写すときは README の同じ命令からが確実です: 
    ffmpeg -f lavfi -i testsrc2=size=1280x800:rate=30 -t 5 -c:v libx264 -profile:v main -bf 0 -g 60 -b:v 8M -x264-params aud=1 -f h264 tabspan_1280x800_30.h264
    6 つの大きさ × 30・60 fps の 12 本をまとめて作る例(PowerShell): 
    foreach ($s in "1280x720","1280x800","1920x1080","1920x1200","2560x1440","2560x1600") {
  foreach ($r in 30,60) {
    ffmpeg -f lavfi -i "testsrc2=size=${s}:rate=$r" -t 5 -c:v libx264 -profile:v main -bf 0 -g 60 -b:v 8M -x264-params aud=1 -f h264 "tabspan_${s}_$r.h264"
  }
}
  3. 作った映像を端末へ置きます。 
    adb push tabspan_1280x800_30.h264 /sdcard/Android/data/io.github.takosasidev.tabspan.probe/files/
    まとめて置くときは、adb push を 1 本ずつ打つか、PowerShell で Get-ChildItem tabspan_*.h264 | ForEach-Object { adb push $_.Name /sdcard/Android/data/io.github.takosasidev.tabspan.probe/files/ } を打ちます。
  4. もう一度「復号のテスト」を押します。ファイル N 本 と出て、測定が始まります。
  5. デコーダーごとに、1 本につき「速さ」と「遅れ」の 2 回を測ります。12 本では数分かかります。--- 終わり --- が出るまで待ちます。
  6. 最後に表と、R-4(1280x800@30 を復号できるか) の行が出ます。読み方は 5 章にあります。

adb から始めるときは次のとおりです(手順 4 の代わり)。

adb shell am start -n io.github.takosasidev.tabspan.probe/.MainActivity --es action decode-test

映像の決まり

  • 名前は tabspan_<幅>x<高さ>_<fps>.h264 の形にぴったり合わせます(例: tabspan_1920x1080_60.h264)。形の違うファイルは数えません。
  • 中身は生の H.264(Annex B)で、各フレームの先頭に AUD が要ります。ffmpeg では -x264-params aud=1 と -f h264 で、この形になります。
  • 測定 1 回は 20 秒で打ち切ります。-t 5(5 秒)くらいの長さにします。
  • 名前に .secure が付くデコーダーは測りません。

4.4 PC の Probe: 画面や入力を変えない命令

次の命令は、結果を出すだけで、画面の構成や入力を変えません。<識別子> には、monitors が出す DeviceName(例: \\.\DISPLAY2)を入れます。

命令やること
monitorsモニターの一覧。名前・識別子・大きさ・位置・付いているか・主モニターか。付いていない物も出します
capture <識別子>そのモニターを 5 秒取り込み、届いたフレームの数・大きさと、カーソルと枠の設定が通ったかを出します
encodersH.264 のエンコーダーの一覧(名前・ハードウェアかどうか)と、使えるプロパティ
encode <識別子>5 秒取り込んで H.264 に圧縮し、フレームの数・キーフレームの数・バイト数・圧縮の時間を出します。ハードウェアのエンコーダーは全部、ソフトウェアは 1 つを試します
adbadb の場所・版・つながっている端末(3.3 節)
tls <port>TLS の待ち受け(4.2 節)
  • capture と encode は、画面が変わらないとフレームが届きません。動いている間は、そのモニターの上でマウスを動かし続けます。
  • 取り込みの間、そのモニターの縁に色の枠が出ることがあります。取り込みが終われば消えます。
  • 取り込んだ絵も、圧縮した中身も、ファイルに保存しません。

4.5 detach と attach(モニターを外す・付ける)

何が起きるか: detach は、選んだモニターを本当にデスクトップから外します。そのモニターの画面は消え、そこにあったウィンドウはほかの画面へ移ります。外した状態は Windows の設定に書かれるので、放っておいても、PC を再起動しても元に戻りません。
戻し方: detach が y を聞く前に出す「同じ位置と大きさに戻す命令」を、そのまま打ちます。控え忘れたときは、Windows の「設定」→「システム」→「ディスプレイ」から付け直せます。
  1. できれば、実在のモニターではなく、別に入れた仮想ディスプレイで試します。.\TabSpan.Probe.exe monitors で識別子を確かめます。
  2. .\TabSpan.Probe.exe detach \\.\DISPLAY2 のように打ちます。
  3. 次の 3 行が出ます。2 行目の命令を、メモ帳などに写して控えます。 
    外す前: 位置 (1920,0)、大きさ 1920x1080              ← 例
同じ位置と大きさに戻す命令: TabSpan.Probe.exe attach \\.\DISPLAY2 1920 0 1920 1080
仮想ディスプレイでないモニターを外すと、その画面は消えます。上の命令で戻せます。
  4. 続けますか [y/N]: に y と打って Enter を押すと外します。ほかのキーなら、何もせずにやめます。
  5. 戻すときは、控えた命令を .\TabSpan.Probe.exe attach \\.\DISPLAY2 1920 0 1920 1080 の形で打ち、確認に y と答えます。
  • 主モニターと、付いている最後の 1 枚は外しません(断りました: と出ます)。
  • attach で位置と大きさを省くと、いちばん右のモニターの右隣に置き、大きさは Windows に任せます。

4.6 touch(タッチを注入する)

何が起きるか: 指定した位置を、指で触ったのと同じように本当に押します。まず 1 回タップし、続けて 3 秒の長押しを 4 回(更新の間隔 50・100・200・500 ms)行います。全部で 15 秒ほどかかります。その位置にあるボタンなどが押され、押された結果は取り消せません。
戻し方: 戻す操作はありません。押されても困らない場所(デスクトップの何も無い所や、何も書いていないメモ帳の上など)を選びます。
  1. monitors の「位置」と「大きさ」から、押す位置を決めます。座標は物理ピクセルで、主モニターの左上が (0,0) です。
  2. 押される場所に、困る物が無いことを確かめます。
  3. .\TabSpan.Probe.exe touch 400 300 のように打ち、確認に y と答えます。
  4. 長押しごとに、押す = 通った・更新 N 回のうち失敗 M 回・離す = 通った のような行が出ます。長押しが途中で切れたかどうかは数字では分からないので、画面で見ておきます。

管理者の権限で動いているウィンドウには、タッチが届きません。

4.7 clock(時計のウィンドウ)

何が起きるか: 黒い地に白い文字で、起動からの経過時間(分:秒.ミリ秒)を出すウィンドウが開きます。画面や設定は変えません。
戻し方: ウィンドウを閉じると終わります。コンソールに 時計のウィンドウ: OK と出ます。

使い道: 時計を PC の画面に出し、それを端末に映した状態で、PC の画面と端末の画面を 1 枚の写真に撮ります。写った 2 つの時刻の差が、映すまでの遅れです。いまは {{ app.name }} 本体が無いので、端末に映すには別のソフトを使います。ウィンドウの大きさを変えると、字の大きさも変わります。

5.3 端末の調べ物

  • 申告: 可 / 不可 は、デコーダーが自分で「この大きさと fps を扱える」と答えた結果です。
  • configure: 成功 は、その大きさでデコーダーを用意できたという意味で、実際に速く復号できるかは分かりません。それを測るのが復号のテストです。
  • dtab d-01J では、申告で「不可」だった大きさも、復号のテストでは実時間より速く復号できました(5.5 節)。

5.4 復号のテストの表

出力の例(デコーダーの名前と数字は、説明のための架空の値です):

--- 表(速さの実測 fps / 遅れの中央値。BB は ByteBuffer の出力で測った物) ---

マスの形意味
400.0fps/8.0ms左が速さ(できるだけ速く入れたときに 1 秒あたり何枚出たか)、右が遅れ(実時間の間隔で入れたとき、1 枚を入れてから絵が出るまでの時間の中央値)
末尾に BBSurface へ復号できず、ByteBuffer の出力で測った
末尾に (140/150枚)入れた数より、出た絵が少なかった

  • 速さが映像の fps(30 か 60)より大きければ、その大きさを実時間で復号できています。
  • 遅れは小さいほど、映すまでの遅れが短くなります。
  • R-4(1280x800@30 を復号できるか) の行は、1280x800@30 の映像を、どれかのデコーダーで全部の枚数、30 fps 以上の速さで復号できたかの判定です。できた・できない・判定できない(その映像を置いていない、または全部のデコーダーで測れなかった)のどれかが出ます。

6. 困ったとき

こうなった見る所・直し方
adb devices に端末が出ないUSB デバッグが有効か(2 章)。線がデータを通せる物か。別の USB の口や線で試す
端末が unauthorized と出る端末の画面の「USB デバッグを許可しますか?」で「許可」を押す。出ていなければ線を抜き差しする
adb の命令で adb の場所: 見つからないPlatform-Tools のフォルダに PATH を通す。winget で Google.PlatformTools を入れてもよい
adb install が INSTALL_FAILED_UPDATE_INCOMPATIBLE で失敗する署名の違う版が入っている。8 章の手順でいったん消してから入れ直す
dotnet build が失敗するdotnet --list-sdks で 10.x の SDK があるか確かめる。無ければ .NET 10 SDK を入れる
端末に TLS の結果: 失敗 と出るPC の 60 秒が過ぎていないか。adb reverse を打ったか。ポートの番号が 3 か所(PC の tls・adb reverse・アプリの欄)で同じか。例外の種類が java.net.ConnectException なら、たいてい adb reverse の打ち忘れ
PC に 待ち受けを開く: 失敗 と出るそのポートを別のソフトが使っている。別の番号(例: 47816)にして、3 か所をそろえる
指紋が違う自分の PC の Probe ではない相手につながっている。結果を信じず、adb reverse --remove-all をしてから、4.2 節を最初からやり直す
復号のテストで ファイル 0 本名前が tabspan_<幅>x<高さ>_<fps>.h264 にぴったり合っているか。置き場: の行のフォルダに置いたか
AUD(NAL 種類 9)が無いので区切れない映像に AUD が入っていない。ffmpeg に -x264-params aud=1 を付けて作り直す
置き場: (getExternalFilesDir が null)端末の記憶域が使えない状態。端末を再起動して、もう一度押す
capture / encode でフレームが 0測っている間、そのモニターの上でマウスを動かす。デスクトップに付いていないモニターは取り込めない
encode でハードウェアが通らない開発者の PC でも、まだ通っていません。ソフトウェアの結果は使えます
detach で 断りました:主モニターと、付いている最後の 1 枚は外さない決まりです
モニターを外したまま戻せない控えた attach の命令を打つ。控えが無ければ、Windows の「設定」→「システム」→「ディスプレイ」で付け直す
touch で 失敗 (GetLastError=…)数字をそのまま控えて報告してください。管理者の権限で動いているウィンドウには届きません

7. 安全とプライバシー

  • 保存しない: 取り込んだ画面、圧縮した映像、測定の結果をファイルに書きません。結果はコンソールと端末の画面(と logcat)に出るだけです。
  • 証明書の鍵: tls は、その場で自己署名の証明書(ECDSA P-256)を作ります。鍵は Windows の利用者の鍵の置き場に一時的に置かれ、Probe が証明書を手放すと消えます。
  • 外へ通信しない: PC の tls は 127.0.0.1 だけで待ち受けます。端末のアプリがつなぐ先も 127.0.0.1 だけで、権限は INTERNET だけです。
  • 証明書を検査しない: TLS のテストは測定用なので、端末は相手の証明書を検査しません。相手は指紋で確かめます(4.2 節)。
  • 実在のモニターも外せる: detach は仮想ディスプレイに限らず外せます。外す前に出る戻す命令を必ず控えます(4.5 節)。
  • 本当に押す: touch は、その位置の物を本当に押します(4.6 節)。
  • 出力を公開の場所に貼らない: PC の Probe の出力には、モニターやアダプターの名前、デバイス ID、adb の場所などが入ります。adb の命令は端末のシリアルと利用者のフォルダの名前を伏せますが、ほかの命令は伏せません。人に見せるときは、名前や ID を消してから貼ります。

8. 片付け

端末

  1. 置いた映像を消します。
    adb shell rm /sdcard/Android/data/io.github.takosasidev.tabspan.probe/files/tabspan_*.h264
    アプリを消すと、このフォルダもいっしょに消えます。
  2. アプリを消します。adb uninstall io.github.takosasidev.tabspan.probe を打つか、端末の「設定」→「アプリ」から「TabSpan Probe」をアンインストールします。
  3. ポートの中継を外します。adb reverse --remove-all
  4. adb を使い終えたら、端末の「開発者向けオプション」で「USB デバッグ」を無効にします。

PC

  1. detach で外したモニターがあれば、控えた attach の命令で付け直します。
  2. Probe が起こした adb のサーバーは、Probe が終わっても残ります。止めるときは adb kill-server を打ちます。
  3. PC の Probe はインストールしていないので、取ったソースのフォルダごと消せば片付きます。作った試しの映像(tabspan_*.h264)も消します。
